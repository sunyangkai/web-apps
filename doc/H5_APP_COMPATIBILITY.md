# H5 与 App 版本兼容治理

## 1. 先定义最低支持版本

- 不再默认支持所有历史 App 版本运行最新 H5。
- 明确最低支持版本，低于该版本直接拦截或提示升级。
- 支持范围必须有时间窗口，例如只支持最近 6 个月或最近 2 个大版本。

**原则**

- 兼容范围是治理策略，不是开发同学临时兜底。
- 没有最低版本，兼容代码会无限累积。

## 2. 重大不兼容变更必须双轨发布

- 先让服务端兼容新旧协议。
- 再发布新版 App 和新版 H5。
- 旧流量下降到阈值后，再删除旧逻辑。

**禁止**

- 同一天同时切接口、切 H5、切 App，并要求所有环境立即一致。

## 3. 契约必须版本化，不能靠隐式约定

- API 返回结构必须保证增量兼容，避免直接改字段语义。
- JSBridge 能力必须有版本或能力声明。
- H5 不允许假设 App 一定存在某个方法、某个字段、某个容器行为。

**要求**

- 先判断能力是否存在，再决定走新逻辑还是降级逻辑。

## 4. 静态资源必须强版本化

- 所有 JS/CSS 资源文件名带 hash。
- HTML 或入口清单短缓存或不缓存。
- 每次发布都必须是完整、不可变的一组资源。
- 发现入口文件和 chunk 版本不一致时，直接刷新或提示重载。

**目标**

- 避免“HTML 是新的，静态资源还是旧的”。
- 避免 WebView 缓存导致半新半旧。

## 5. 用能力探测替代大量版本判断

- 版本号用于决定是否允许进入。
- 能力探测用于运行时分支。
- 对桥接能力、登录能力、上传能力、支付能力分别探测，不要只写 `version >= x.y.z`。

**原因**

- 同版本号不一定代表同能力，渠道包、定制包、热修复都可能不同。

## 6. 旧版本要有明确退出机制

- 每一段兼容逻辑都要写删除条件。
- 每一个旧协议都要写下线日期。
- 每次迭代都检查哪些兼容代码可以删除。

**禁止**

- 只加兼容，不设失效时间。

## 7. 兼容策略要能远程控制

- 服务端返回当前 App 版本是否允许访问某功能。
- 通过远程配置控制强制升级、灰度开放、降级页、熔断开关。
- 出现线上问题时，优先用配置止血，不依赖重新发版。

## 8. 发布流程必须包含兼容检查

- 发布前确认本次是否引入新的 App 能力依赖。
- 发布前确认旧接口是否仍在支持窗口内。
- 发布前确认静态资源缓存策略不会产生脏版本。
- 发布后持续观测旧版本流量占比，再决定何时删除兼容逻辑。

## 最小落地方案

1. 定义最低支持 App 版本。
2. H5 启动时上报 `appVersion` 和能力清单。
3. 服务端返回是否允许访问、是否需要升级、是否需要降级。
4. 重大变更按“新旧双轨”发布。
5. 静态资源全部 hash 化，入口短缓存。
6. 兼容分支统一登记删除时间。

## 判断标准

- 不能删除的兼容逻辑，说明边界没定义清楚。
- 需要长期维护的旧协议，说明版本策略失效。
- 每次发版都担心旧版本，说明治理问题大于代码问题。
